## 1. 现状概述

### 1.1 技术栈与核心类

模块由两个文件承载（合计约 1580 行）：

| 文件 | 职责 | 核心类/函数 |
|------|------|------------|
| `rpa_engine/gui/node_graph.py`（789 行） | 场景渲染与图元 | `NodeGraphScene(QGraphicsScene)`、`NodeGraphView(QGraphicsView)`、`TableNode`/`StepNode(QGraphicsObject)`、`ConnectionItem(QGraphicsPathItem)`、`_StatusDot`/`_DotMarker`/`_ForkMarker`、`GraphLayoutData`/`StepLayoutEntry`（纯数据） |
| `rpa_engine/gui/page_operation_config.py`（图相关段） | 数据组装与交互接线 | `_refresh_graph()`（L448-537，唯一数据组装点）、`update_step_status`/`set_step_runtime_status`/`reset_runtime_status`（L539-561）、`_on_node_step_selected`/`_on_table_reorder` |

### 1.2 渲染模型

- 基于 **QGraphicsScene/View 位图式图元渲染**（非 Canvas/SVG/WebGL），图元均为固定尺寸：表节点 160×40、步骤节点 140×54、交点圆点直径 12（`node_graph.py:42-51`）。
- 连线为 `QPainterPath moveTo+lineTo` **纯直线**（L615-627），纵向列线（输入灰/派生蓝，宽 2.0）+ 横向数据流线（灰，宽 1.5）+ 独立三角箭头 `QGraphicsPolygonItem`（size 9，z=6）。
- z 层级散布 6 处硬编码：连线 -1 < 表/圆点 0 < 步骤节点 1 < 标记 5/6 < 高亮 10（L290/359/399/421/636/571）。

### 1.3 数据流

```
WorkflowModel.steps/_table_entries（models.py）
  → OperationConfigPage._refresh_graph()（page:448-537，10 处触发点）
    → GraphLayoutData(表显示名列, StepLayoutEntry 行, input_count)
      → NodeGraphScene.rebuild()（node_graph:468-548：clear() → 全量重建 → setSceneRect）
        → fit_to_scene()（page:537 每次 rebuild 后必调）
```

布局为**自定义坐标计算**（非力导向/层次布局）：表→列（按 `table_aliases` 枚举序，L490-492）、步骤→行（列表索引，L511）；步骤节点 x 取其输入/输出列区间的**中点**（L513-517），y 按行固定——形成"泳道网格 + 骑跨中点"的混合坐标参考系。

### 1.4 交互现状

- 图→表单单向选中：`StepNode` 点击 → `step_selected` → 右侧面板切换（page:345-349）；反向高亮不存在（`highlight_step` L563-571 全仓库无调用者）。
- 表序调序：表节点顶部 "left/right" ASCII 文字按钮（BTN_H=18）逐格交换（page:407-422）。
- 视图：Ctrl+滚轮缩放（因子硬编码 1.15/0.87，无范围限制 L782-789）+ 空白处拖拽平移（自实现，L746-780）。
- 运行时状态：worker 信号 → 节点四色（2026-08-31 已接线），但仅经 `update_step_status` 单点更新路径生效。
- **显隐控制：完全缺失**（全文件 `setVisible`/`hide()` 出现 0 次）。

## 3. 根因分析

### 根因 A：状态更新与渲染分离不彻底（P0-1/P1-5 的根源）

`rebuild()` 是唯一的"真相刷新"路径，而**视图状态（缩放、平移、选中、运行时状态色）寄居在图元 item 上**——`clear()` 一执行，视图状态随图元一起被销毁，且无任何保存/恢复逻辑。这不是某个 bug，而是"数据变化 → 全量重绘"这一最朴素渲染模型 Direct：缺少一层"图内容"与"视图状态"的职责分离。

### 根因 B：坐标参考系设计错位（P0-2 的根源）

布局采用"**表→列、步骤→行**"的电子表格心智（泳道图），但步骤节点 x 又取输入/输出列中点，使步骤脱离网格交点、沿对角线漂移；同时场景矩形按**列数**（表数）而非**内容实际包围盒**计算，两者叠加造成"内容挤在对角线、画布大片空白、fit 后过小"。列中心、行中心、场景尺寸三套坐标各处独立硬算，缺少统一的坐标映射层（LayoutEngine）。

### 根因 C：连线无路由模型（P0-3 的根源）

边被简化为"两端点直线"，端点锚定在**列中心/行中心/节点中心**这类几何中心上，而非节点边缘端口；箭头锚在节点中心 x 上，与 z=6 叠加直接刺入节点。没有边路由（正交折线、通道分配、避障）概念，拓扑一旦出现长距离依赖（如 merge 步骤引用远处输入表），连线必然横穿全图。

### 根因 D：布局算法与问题域不匹配（P0-2/P1-1 的深层原因）

节点图的语义是 **DAG**（步骤有明确上下游拓扑），但当前布局不计算拓扑层次——上下游关系仅靠"派生表列位置在输入表之后"隐式表达；fork/merge 语义靠 `_ForkMarker` 菱形、merge 橙点等**视觉补丁**标注而非结构表达。步骤数与分支数增长时，泳道+中点模型既不减少交叉也无法表达并行分支，且没有任何显隐/聚焦手段给用户"降维"视图。

### 根因 E：交互契约未完整定义（P1-2/P1-4 的原因）

选中是单向的（图→表单），信号契约存在残留死代码（`highlight_step`、`table_selected(alias)` 的 alias），装饰图元未纳入事件体系（既非可点也非穿透）。反映开发时未定义"图上每个元素的交互语义表"，哪些可点、点了怎样、选中态如何双向同步没有统一约定。

## 4. 影响评估

| 维度 | 实际负面影响 |
|------|-------------|
| **用户体验** | ① 编辑任何一步（含改目标表下拉）全图销毁重建 + 视图重置，操作流被打断；② 流程超过 ~6 步或存在跨表合并时，阶梯布局+长横线+交叉线使图不可读，fit 后节点文字不可辨认；③ 失败排查时节点状态可能已随重建归零，图失去"定位故障步骤"价值；④ 缩放无边界，误操作后难以回到合适视野 |
| **开发维护** | ① `_refresh_graph`（90 行）与 `rebuild`（80 行）+ 4 个 `_build_*` 私有方法强耦合坐标计算，任何视觉调整需同时理解约 12 个布局常量；② 状态丢失类 bug 的修复被架构堵死——不做状态分离，任何修补都是绕过；③ 死代码与 5 处注释漂移持续误导后续开发 |
| **扩展性** | ① 无法新增节点类型/右键菜单/minimap/子图折叠（无挂点）；② 显隐、聚焦、局部刷新均无法在不推翻 rebuild 模型的前提下实现；③ 布局常量散布使"换一种布局算法"等于重写 |

## 5. 改进方向建议（高层次思路，不含具体代码）

### 5.1 引入"视图状态 × 图内容"分离层（解决 P0-1/P1-5）
建立视图控制器持有 zoom/pan/selection/runtime-status，`rebuild` 前后由控制器保存并恢复；中期演进为**差量刷新**（diff 节点/边集合，仅增删变化的图元）。运行状态从"构造参数"改为场景可查询的独立状态源。

### 5.2 抽取统一布局引擎（解决 P0-2）
新增纯函数式 LayoutEngine：输入 (tables, steps, 约束)，输出 `{节点→场景矩形, 边→路径点集, 场景尺寸}`——可单测、可替换；场景退化为"消费布局结果的渲染器"。**场景尺寸一律取内容包围盒+边距**，杜绝按列数撑画布。

### 5.3 边路由与端口锚点（解决 P0-3）
连线改为正交折线（HV/VH），锚点改到节点**边缘端口**（输入口在左/上，输出口在右/下），箭头贴端口绘制；交叉处按行/列分配通道，必要时桥接弧。彻底消除"箭头扎入节点"与"横穿全图"。

### 5.4 布局算法向 DAG 语义演进（解决根因 D，长期）
从"表列泳道"迁移到分层 DAG 布局（拓扑分层 + 重心法减少交叉），表节点可作为特殊层或保留泳道但由 LayoutEngine 统一排布；现有 left/right 手工调序保留为"用户约束"输入。自研（业务规模小，约百级节点）或引入轻量分层布局思想均可，不建议引入重型图引擎依赖（违背轻量打包约束）。

### 5.5 交互语义补全（解决 P1-1/P1-2/P1-3/P1-4）
定义"图元素交互语义表"：可点（表/步骤）、可拖（表列序）、可穿透（装饰点）、可框选（留白）；补双向选中高亮、hover 完整名 tooltip、节点显隐/聚焦模式（如"仅看某表下游"）；缩放加 0.4–2.5 边界 + resize refit + 初始 setSizes 固定 6:4。

### 5.6 常量与层级收敛（解决 P2-2/P2-3）
布局常量收敛为单一 LayoutConfig 数据类；z 层级定义枚举（Background=-1, Node=0, Decorator=5, Overlay=10）；修正 5 处注释漂移。

## 补充分析：位置错乱与重叠问题专项诊断（2026-09-01 追加）

> 触发背景：真机测试持续暴露"标识信息（节点标题、端口标签、连线标注等）渲染成功，但屏幕绘制位置严重偏离设计预期，多元素频繁堆叠、交错混杂"。本节为现象导向的专项诊断，与正文各章节的机制层剖析交叉引用、互为补充。本轮同样只分析未修改任何源码。

### S1. 与原报告的交叉验证结论

**机制层已涵盖，现象层为本节补充。** 具体映射：

| 本现象的构成面 | 原报告已覆盖位置 |
|---------------|----------------|
| 流程呈对角阶梯漂移、内容挤在画布一角、fit 后节点过小难辨（"位置偏离预期"的主观感受来源） | §2 P0-2（坐标参考系错位 + 场景尺寸与内容脱钩）；§3 根因 B |

### S2. 现象复现路径

**复现条件**：阶段 2 操作配置页，已导入 ≥1 张数据表，流程配置 ≥3 步且包含跨表操作（mapping_match/merge_tables）。

1. 依次添加：筛选（T1→T3）→ 跨表映射匹配（T3+T2→T4）→ 条件统计（T4→T5）→ 数据表合并（T5+T2→T6）→ 结果导出（T6）。
2. 观察节点图：步骤节点沿对角线阶梯下坠；合并步骤的输入线从远处表列横穿画布；每个步骤节点内部出现箭头三角（合并步骤为两枚"蝴蝶结"）；合并输出交点处只见一颗橙色圆点（绿色状态点被覆盖）。
3. Ctrl+滚轮缩放至合适视野，随后**增删/移动任一步骤或仅切换某步骤的目标表下拉**：全图销毁重建，视角强制回 fit 全景，缩放/平移/选中全部丢失。
4. 拖动窗口改变大小：画布内容整体位移（ResizeAnchor=AnchorUnderMouse 保持鼠标下场景点不动，其余内容相对移动）。

### S3. 四大坐标假设逐项排查结果（代码级）

| 假设 | 结论 | 代码证据 |
|------|------|---------|
| ① 相对坐标与绝对坐标混用 | **部分成立（工程瑕疵，非 bug）**——两套坐标约定并存且各自自洽 | 节点类用 `setPos` 场景坐标：TableNode `setPos(x, y)`（node_graph.py:216、504）、StepNode（:287、522）；装饰类把**绝对场景坐标直接烤进图元几何**：`_StatusDot` 构造矩形偏移（:341）、`_DotMarker` 椭圆（:395-396）、`_ForkMarker` 多边形顶点（:412-417），item pos 恒为 (0,0)。子标签 `QGraphicsSimpleTextItem` 挂在椭圆 item 下、用父 item 坐标 `setPos(d/2+3, -d/2-2)`（:401-403），因父 item 原点即场景原点，换算结果 (x+3, y-d-2) 恰为圆点右侧，**数学正确但依赖"矩形烤坐标"约定，若未来移动图元极易出错** |
| ② 父容器偏移未叠加 | **不成立** | 除上述子标签外全部为顶级图元（parent=None 默认），场景中不存在 QGraphicsItemGroup/容器嵌套；页面侧无任何手工坐标叠加（图放置完全由视图部件内部管理） |
| ③ 缩放/平移变换未正确应用 | **不成立（机制标准），一处不一致除外** | `fitInView(rect.adjusted(-10,-10,10,10), KeepAspectRatio)`（:740）、缩放锚 `AnchorUnderMouse`（:729）、滚动条平移（:765-768）均为 Qt 标准用法，场景→视口映射无手工变换。例外：命中判定 transform 不一致——scene 用视图变换（:703）vs view 用单位变换（:752-753），缩放状态下对同一光标的"空白"判定可能分叉（已在正文 §2 P1 记录，此处归档到坐标主题） |
| ④ 渲染更新中的坐标重置/累积偏移 | **不成立（无累积）；"跳变"另有成因** | `rebuild()` 每次 `clear()` 后从模型数据全量重算（:474-548），图元几何无跨重建状态延续，数学上不可能累积偏移；`update_step_status` 仅 `update()` 重绘不改坐标（:292-295）。用户感知的"位置跳变"来自两个标准行为叠加：rebuild 后强制 `fit_to_scene` 重置视角（:537 页侧必调 + :740）+ `setResizeAnchor(AnchorUnderMouse)`（:730）使窗口缩放时内容整体位移 |

### S4. "堆叠交错"三项新发现（原报告未记录）

1. **标记点同坐标堆叠（数学必然）**：merge 步骤的输出交点上，状态圆点 `_StatusDot(列中心, 行中心)`（:532，z=0）与合并标记 `_DotMarker(列中心, 行中心)`（:688，z=5）**坐标完全相同**，橙色（z=5）永久覆盖绿色输出点（z=0）；fork 步骤的分叉菱形（:680-684，z=6）同理覆盖 primary_input 交点圆点。真机表现为"端口标识丢失/只剩一个色点"。
2. **箭头入节点为几何必然**：横向输入线终点 = 节点中心 x（:657、`_add_arrow_line(cx, y, node_cx, y)`），箭头尖端即线终点且 z=6（:636）高于节点 z=1；节点半宽 70 < 相邻列距 120，故箭头（长 9px）必然落在节点内部文本区——真机表现为"节点标题被三角遮挡"。附带排除项：**步骤节点互相之间不重叠**（行距 V_SPACING=100 > 节点高 54，每步独占一行），堆叠只发生在"箭头×节点"与"标记×圆点"两类。
3. **双重 setPos 冗余**：TableNode/StepNode 构造时已 `setPos(x, y)`（:216/:287），创建处却传 (0,0) 后再二次 `setPos`（:502-504/:521-522）——无害但掩盖定位意图，易误导维护者以为存在两套定位来源（与假设①的双约定问题同源）。

### S5. 分层根因判定

```
"位置错乱与重叠"现象
├─ 层级 1｜布局算法缺陷（主因，约七成感知权重）
│    步骤节点 x 取输入/输出列区间中点骑跨（:516-517）→ 对角阶梯漂移；
│    场景矩形按表总数而非内容包围盒（:543-548）→ fit 后整体过小、
│    内容偏居一角。对应正文根因 B。
├─ 层级 2｜渲染更新机制（次因，"不稳定/跳变"感知来源）
│    rebuild 全量重建 + fit 强制重置视角（无累积偏移，重置即跳变）；
│    ResizeAnchor=AnchorUnderMouse 放大窗口操作时的位移感。
│    对应正文根因 A / P0-1。
├─ 层级 3｜连线与标记的锚点设计（"堆叠交错"直接来源）
│    直线锚节点中心 + 箭头 z=6；merge/fork 标记与状态点同坐标堆叠。
│    对应正文根因 C / P0-3，及本节 S4。
├─ 层级 4｜坐标映射断层——【排除】
│    场景→视口映射全程 Qt 标准机制，无手工变换、无父偏移遗漏、
│    无累积误差（S3 假设②③④均排除）。
└─ 层级 5｜工程瑕疵（放大维护误判，非运行时成因）
     双坐标约定并存、双重 setPos、命中判定 transform 不一致（S3①③）。
```

### S6. 与既有问题的关联性结论

本现象**不是独立新缺陷**，而是正文 **P0-2（坐标参考系错位）+ P0-3（连线锚点/路由缺失）+ P0-1（重建重置）** 三个已知问题在真机上的复合感知表现，外加 S4 两项此前未记录的堆叠细节。修复优先级不变：正文 R1（视图状态保持 + 箭头改节点边缘端口）可消除"跳变"与"箭头入节点"两大感知来源；R2（布局引擎 + 内容包围盒）消除阶梯漂移与 fit 过小；S4-1 标记堆叠应并入 R3（边路由与标记布点）一并处理。
