# Agent 运行方式判定规范

> 所属层级：知识层（docs/），经 AGENTS.md §2.5 背书具 [约束] 效力
> 适用范围：Agent 接到任何任务后、执行实际操作之前的运行方式判定；多 Agent 模式选定后的运行期协作规范（§6）
> 最后更新：2026-09-13（§6 新增「编码类角色集」，来源 G-6；历史 2026-09-06：§6 多 Agent 协作规范自 AGENTS.md §3.1 迁入）｜可信度状态：[已校验一致]（模式定义按规约标准落地；环境能力检测已于 2026-08-18 实测通过——本项目环境成功并行派发 3 个子 Agent）

## 1. 模式定义

| 模式 | 名称 | 适用条件 | 执行方式 |
|------|------|----------|----------|
| A | 单 Agent 直接执行 | 任务范围小（参考阈值：涉及文件 ≤5 个且模块 ≤2 个，可按项目调整）、上下文可控、无需拆分 | 一个 Agent 顺序完成全部操作 |
| B | 多 Agent 协作执行 | 任务复杂（参考阈值：涉及文件 >5 个或模块 >2 个）、涉及多模块/多文件、环境支持子 Agent 派发 | Orchestrator 拆分任务，多 Agent 并行/串行协作 |
| C | 单 Agent 降级执行 | 环境不支持多 Agent，但任务本身复杂度较高 | 单 Agent 分步骤串行执行，每步仅加载当前步骤所需上下文 |
| D | 混合模式 | 环境仅支持部分协作能力（如可派发子 Agent 但不支持并行），需按环节混合串并行，且与模式 B 互斥：环境完整支持协作时不得选用本模式 | 按环节混合使用，明确标注哪些步骤并行、哪些串行 |

## 2. 模式选择判断标准

Agent 在读取本文档后，必须依据以下维度进行判定：

- **任务复杂度**：涉及文件数量、模块数量、操作类型（读/写/创建/删除）
- **上下文规模**：预计需要加载的文档/代码总量是否超出单次上下文窗口
- **环境能力**：当前 Agent 环境是否支持子 Agent 派发（检测方式见 §3）
- **任务耦合度**：各子任务之间是否存在强依赖（有则倾向串行）

判定顺序：先看任务复杂度定候选（小→A，大→B）；再用环境能力检测验证 B/D 候选；检测失败按 §4 降级。

## 3. 环境能力检测方法

以下检测步骤可直接执行：

1. **尝试派发一个最小子任务**：向子 Agent 派发任务"读取仓库根的 README.md（相对本文件为 `../README.md`）第一行并返回"。
   - 成功的表现：子 Agent 返回该行内容（"# V3 - 当前重构升级版本"或等价标题行）
   - 失败的表现：派发机制报错、无响应或超时
2. **检测是否存在子 Agent 派发机制**（Task Delegation / Worker / Sub-Agent）：检查当前 Agent 工具集中是否存在 Agent/Task 类派发工具。
   - 成功的表现：工具存在且可构造调用
   - 失败的表现：工具不存在或调用被拒绝
3. **降级联动**：若原判定为模式 B 或模式 D 且上述检测失败，自动降级为模式 C；若原判定为模式 A，维持模式 A。

本项目当前环境能力：支持多 Agent 协作（2026-08-18 实测，三层规约体系构建任务中并行派发 Scanner + 2×Verifier 成功）[已校验一致]

## 4. 降级策略

- **降级条件**：模式 B → 模式 C（环境不支持子 Agent 派发）；模式 D → 模式 C 或模式 A（部分协作能力失效且任务可串行化；任务范围缩至阈值内时可降至 A）
- **切换流程**：在输出中声明降级事实与原因 → 重新按目标模式规划步骤 → 继续执行，不中断任务
- **流程一致性**：降级后中间结果仍写入 `_temp/`（校验类 `verify-*.md`、推测类 `infer-*.md`），保持与多 Agent 模式一致的可追溯性
- **输出注明**：降级后必须在运行方式声明中注明实际执行模式与降级路径（见 §5）

## 5. 输出声明要求

Agent 确定运行方式后，必须在任务开始时输出（本条款自规约体系建成后的任务起生效，规约构建任务本身不适用）：

```
🔧 [运行方式]
- 选择模式：A / B / C / D
- 判定依据：（简述）
- 环境能力：支持多Agent / 不支持多Agent
- 降级情况：无 / 已从 B 降级至 C / 已从 D 降级至 C 或 A
```

## 6. 多 Agent 协作规范（运行期）

本项目支持多 Agent 协作模式，遵循以下原则：

1. **最小上下文原则**：每个 Agent 仅加载完成任务所需的最小文档集合
2. **任务传递仅含指令+路径**：Agent 间传递任务时不传递文档全文，仅传递指令和文件路径
3. **子 Agent 仅返回摘要**：子 Agent 完成任务后仅返回结果摘要或变更清单；详细校验结果写入 `_temp/verify-*.md`，详细推测结果写入 `_temp/infer-*.md`，不返回全文
4. **禁止全量加载**：任何 Agent 不得一次性加载整个规约体系

推荐分工架构（构建类任务按需启用）：

| 角色 | 职责 | 加载的上下文 |
|------|------|-------------|
| Orchestrator（主控） | 任务拆解、分发、汇总、校验调度 | 仅 AGENTS.md + 决策报告 |
| Scanner Agent | 现状扫描与评估 | 仅目录结构 + 各文件首 20 行 |
| Verifier Agent(s) | 一致性校验与有限推测 | 仅目标模块代码/配置 + 对应文档片段 |
| Writer Agent(s) | 具体文档的创建/改写 | 仅目标文档相关的已有内容 + _temp/ 结果 |
| Indexer Agent | 创建/维护各层索引文件 | 仅对应目录文件列表 + 各文档标题摘要 |
| Auditor Agent | 执行全局更新校验流程 | 按步骤按需加载 |

**编码类角色集（2026-09-13 新增，来源 G-6；承自 2026-09-02《规约体系结构性缺口》方案 §3.9）**

代码实现类任务按需启用以下角色：

| 角色 | 职责 | 加载的上下文 |
|------|------|-------------|
| Coder Agent | 按已裁定方案实现代码（只改源码，不改规约） | 仅目标模块源码 + 对应规约片段 |
| Reviewer Agent | 按规约复核代码：`AGENTS.md` §2 红线 + `docs/doc-governance.md` §7 同步检查清单 | 变更 diff + `AGENTS.md` §2 + 相关 docs 片段 |
| Tester Agent | 执行验收并留痕（依据 `docs/doc-governance.md` §8 验收与回归记录规范） | 已裁定的验收条目 + 实际可执行的验证手段 |

> **声明（两套角色集不混用）**：文档构建类任务沿用 Scanner / Verifier / Writer / Indexer / Auditor；代码实现类任务启用 Coder / Reviewer / Tester。同一任务如需跨越两类，由 Orchestrator 按阶段切换并显式声明当前角色集。
> **与职责矩阵的关系**：`docs/doc-governance.md` §2 维护职责矩阵按"责任人"维度描述，本节按"运行期分工"维度描述，二者互补、不构成重复。
