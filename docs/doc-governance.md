# 文档治理与维护规范

> 所属层级：知识层（docs/），经 AGENTS.md §2.5 背书具 **[约束]** 效力（违反即为执行错误）；与 AGENTS.md 冲突时以 AGENTS.md 为准
> 适用范围：规约体系全部文档的变更操作、维护职责、生命周期与元信息区、全局更新校验、实例文档维护
> 迁移来源：§1~§5 = 原 AGENTS.md §7.1~§7.5（2026-09-06 精简剥离）；§6 = 原 AGENTS.md §4.6（2026-09-13 精简下沉）。§7~§10 为 2026-09-13 新增（§7/§8 承自 2026-09-02《规约体系结构性缺口》方案的 G-4/G-5，落点由已失效的 AGENTS.md §7.7/§7.8 改迁至此）。本文件为这些细则的唯一载体，AGENTS.md 侧仅保留核心条款与索引/指针

## 1. 文档变更操作规范

1. 任何规约文档变更后（新建、删除、修改、移动、重命名），必须立即执行"全局更新校验机制"（§4）
2. 新增知识层/实例层文档必须包含 YAML 元信息区（§3 字段规范），正文保留标题与适用范围说明
3. 文档间引用使用相对路径
4. 已有文档可用的内容必须保留，可移动/重组/改写格式，但信息不得丢失
5. 若某份已有文档内容已过时，标注 `[已过时-待确认]`（对应 status: deprecated 待确认）而非直接删除
6. 实例文档生命周期操作（新增/移动/删除/知识层更新/路径失效）按 §5 联动规则执行

## 2. 维护职责矩阵

| 操作 | 责任人 | 触发条件 | 校验要求 |
|------|--------|---------|---------|
| 新增知识层文档 | 开发者/Agent | 新领域知识产生 | 更新 `docs/INDEX.md`，添加元信息区 |
| 新增方案态文档 | 开发者/Agent | 新实施计划产生 | 更新 `docs/plan/INDEX.md`，添加元信息区 |
| 新增实例文档 | 开发者/Agent | 新模块/功能上线 | 更新 `knowledge/Instances-INDEX.md`，添加元信息区 |
| 修改约束层 | Tech Lead / 架构师 | 规则变更 | 全局影响评估，通知所有相关方 |
| 废弃文档 | 文档 Owner | 内容过时 | 标记 `status: deprecated`，保留 30 天后归档 |
| 重构文档结构 | Tech Lead | 结构不合理 | 全量链接检查，更新所有 INDEX |

> 本项目角色映射：上表各角色由 黄泊凯（OPERATOR）与协作 Agent 共同承担；变更追溯以 task-records 任务记录为主（原 `_temp/BackUp` 快照机制已于 2026-09-14 随 `_temp` 清理移除，R4；git 操作由人工接管，Agent 不执行——2026-09-01 裁定）。
>
> **2026-10-24 口径细化**：Git 写操作（提交/推送/拉取/分支/合并/变基/回退/暂存/清理等）一律人工接管；Agent 仅只读 `git status`/`git diff`/`git show`/`git log` 可用于比对差异，不得改变工作区、索引或版本库状态。

## 3. 生命周期操作与元信息区

生命周期状态：

| 状态 | 含义 | 允许操作 |
|------|------|---------|
| `draft` | 草稿，未审核 | 编辑、提交审核 |
| `active` | 生效中 | 编辑（需记录变更）、引用 |
| `implemented` | 方案已实现，待沉淀（方案态层专用） | 触发"转知识"：规范内容迁入知识层文档，方案本身转 `archived` |
| `deprecated` | 已废弃，待归档 | 只读，不再引用 |
| `archived` | 已归档 | 只读，仅用于历史追溯 |
| `exempt` | 豁免（经正式审批） | 按豁免条款执行 |

映射规则：旧体系 `[已过时-待确认]` 标记 ↔ `status: deprecated`（待确认）；实例文档 `overrides` 豁免引用 ↔ `status: exempt`；Instances-INDEX 登记清单 status 列与文档元信息区状态保持同步。

YAML 元信息区规范（所有知识层和实例层文档必须包含，INDEX 文件同样适用）：

```yaml
---
title: <文档标题>
type: constraint | knowledge | plan | instance | index | config
scope: global | domain | instance
status: draft | active | deprecated | archived | exempt
owner: 黄泊凯
last-updated: YYYY-MM-DD
tags: [<标签列表>]
---
```

项目扩展字段（不丢失既有信息）：`binding`（四档：constraint / reference / self_contained / pending_ruling，与 `AGENTS.md` §4.5 的四种约束力标签一一对应，落位规则见 §9）、`confidence`（可信度状态，取值 = `AGENTS.md` §4.7 六标签之一）、`governance`（instance 身份标识）、`inherits_from`、`overrides`、`version`、`content-revision`（文档内容原始修订日期，与文件改动日期 last-updated 区分）。

## 4. 全局更新校验机制

**触发条件**：任何规约文档变更完成后（新建、删除、修改、移动、重命名），**无论之前是否校验过、无论提示词是否要求**，必须执行以下校验。多 Agent 模式下由 Orchestrator 调度 Auditor Agent 分步执行，每步仅加载该步所需文件，禁止合并。

**五项校验**（每次变更必查）：

1. **链接完整性**：所有相对路径链接目标存在
2. **元信息完整性**：所有知识层/实例层文档包含必填字段且取值合法
3. **层级一致性**：无实例层内容出现在知识层，反之亦然；约束层不含具体实现细节/领域知识
4. **INDEX 同步性**：所有文档在对应 INDEX 中有条目，无幽灵条目、无遗漏
5. **约束力合规**：无文档违反约束层规则

**脚本化辅助（R6/E1 新增，2026-09-24）**：校验项 1（相对链接可达）、4 的日期口径（`docs/INDEX.md` 日期列 ↔ 各文档 frontmatter `last-updated`）与 `AGENTS.md` 容量三口径/行尾约束（§10）可运行 `python tools/doc_verify.py` 一键核查（仓库根执行，纯标准库）；报告落 `_temp/verify-<YYYYMMDD-HHMM>.md`（留痕，不覆盖历史），退出码 0=全绿。校验项 2/3/5 及 Step 1-3 的语义检查仍需 Agent/人工执行，脚本不替代完整流程。

**`[待补充]` 项处置**：不中断整体流程，将该项写入 `_temp/verify-*.md` 的"待人工介入"专节，继续完成其余工作；最终汇报中单列待介入清单，由用户决定补充方式。（原 AGENTS.md §4.7 末段，2026-09-06 精简迁入）

**三步执行流程**：

**Step 1 — AGENTS.md 自洽性审计**

- 仅加载 `AGENTS.md`
- 检查：逻辑自洽、各板块无矛盾；路由链路声明完整且 markdown 链接有效（[docs/INDEX.md](INDEX.md)、[docs/plan/INDEX.md](plan/INDEX.md)、[knowledge/INDEX.md](../knowledge/INDEX.md)、[knowledge/Instances-INDEX.md](../knowledge/Instances-INDEX.md)、[docs/agent-execution-mode.md](agent-execution-mode.md)）；执行模式判定规则板块存在；v2.2 §5.1 七类章节完整（项目上下文/核心规则/执行模式判定/文档体系路由/全局约束/子目录职责边界/维护与校验）；四层结构（AGENTS.md §4.1）与路由链路（AGENTS.md §4.2/§4.3）及管辖范围（AGENTS.md §5.1 条 6）表述一致；校验机制完整；约束力标签一节（AGENTS.md §4.5）包含全部 4 个标签、可信度标签一节（AGENTS.md §4.7）包含全部 6 个标签及含义，且本文件其余位置出现的标签拼写与用法与其一致；锚点机制摘要（AGENTS.md §7.3）与锚点层（当前任务锚点）齐备、[docs/anchor-mechanism.md](anchor-mechanism.md) 链接可达
- 有问题则修正后重新审计；重新审计最多 3 轮，仍不通过的输出未通过项清单与原因，标注 `[待补充]`，终止本轮校验并在最终汇报中置顶说明

**Step 2 — 索引一致性与五项校验**

- 仅加载：`docs/INDEX.md` + `docs/` 目录文件列表；`docs/plan/INDEX.md` + `docs/plan/` 目录文件列表；`knowledge/INDEX.md` + `knowledge/` 目录文件列表；`knowledge/Instances-INDEX.md` + 全库携带 `governance: instance` 的文档清单；按需抽查各文档元信息区
- 比对：
  - `docs/INDEX.md` ↔ `docs/` 实际知识文档：无幽灵条目、无遗漏（task-records/ 与 plan/ 不计入知识文档）；每条记录的路径实际存在；标题与文件一级标题一致；摘要不超过一句话；可信度状态为六个标签之一且已填写；task-records 声明存在
  - `docs/plan/INDEX.md` ↔ `docs/plan/` 实际方案文档：一一对应，无幽灵条目、无遗漏；[待裁定] 条目标注在案
  - `knowledge/INDEX.md` ↔ `knowledge/` 实际文件（仅两个 INDEX）与领域清单：一一对应，无幽灵条目、无遗漏
  - `knowledge/Instances-INDEX.md` ↔ 全库携带 `governance: instance` 的文档：一一对应，无幽灵条目、无遗漏，登记的每条实例路径实际存在，inherits_from 路径实际存在
  - 五项校验逐项执行：相对链接全量可达、元信息必填字段完整且取值合法、层级内容无越界、INDEX 同步、无违反约束层规则
- 不一致则修正

**Step 3 — README.md 同步更新**

- 仅加载 `README.md` + 相关文档摘要（不读全文）
- 确保信息准确、无约束条款、关键信息带可信度标签
- 有变化则更新

**校验完成确认格式**：

```
✅ [校验通过]
- AGENTS.md：自洽，无矛盾，路由链接完整有效，七类章节完整，可信度标签规范完整，锚点机制摘要/锚点层齐备
- docs/INDEX.md：N 篇知识文档，索引与实际文件一一对应，task-records 声明在案，可信度状态已填写
- docs/plan/INDEX.md：M 个方案文档，索引与实际文件一一对应，[待裁定] 条目标注在案
- knowledge/INDEX.md：领域索引与实际一致
- knowledge/Instances-INDEX.md：M 个实例，注册与全库实例文档一一对应
- 实例文档：元信息区完整（含必填字段），正文无跳转指令
- 链接/元信息：相对链接全量可达，YAML 必填字段完整合法
- README.md：已同步，信息准确，关键信息带标签
- _temp/：校验/推测中间产物已生成并可追溯
- 协作模式：多 Agent 协作 / 单 Agent 降级
- 执行路径：新建 / 局部补全 / 重构规范化 / 校验修正
```

## 5. 实例文档维护

**身份判定规则**：

- 任何 Markdown 文档头部元信息区含 `governance: instance` 即视为实例层管辖
- Agent 遇到此类文档应通过 `knowledge/Instances-INDEX.md` 确认注册状态
- 未注册但携带标识的文档，Agent 应报告注册缺失，不得自行补录

**生命周期联动规则**：

| 场景 | 必须动作 |
|------|---------|
| 新增实例 | ① 实例文档写入元信息区（v2.2 必填字段 + governance/inherits_from/overrides 等扩展字段）；② Instances-INDEX 登记清单新增一行；③ knowledge/INDEX.md 领域清单同步 |
| 移动实例 | ① 更新 Instances-INDEX 登记路径；② 更新 knowledge/INDEX.md 领域清单路径 |
| 删除实例 | ① Instances-INDEX 移除；② knowledge/INDEX.md 领域清单移除；③ 确认无其他文档引用 |
| 知识层规范更新 | 通过实例元信息区 `inherits_from` 反向定位所有受影响实例，逐一校验正文是否矛盾 |
| 路径失效 | 标注 `[路径失效]`，报告 Orchestrator，不自行猜测 |

**继承与豁免说明**：

- 实例只能继承和扩展知识层规范，不得覆写或矛盾；偏离须先在知识层规范中新增编号豁免条款，再在实例元信息区 `overrides` 字段引用
- 实例正文自包含：不得出现"详见知识层 XX"类跳转指令，执行所需信息在文档内完整呈现
- 元信息区 `inherits_from` 仅供回溯维护使用，执行时仅阅读正文

## 6. 冲突解决与豁免

> 效力来源：经 `AGENTS.md` §2.5 背书具 **[约束]** 效力（内容自 `AGENTS.md` §4.6 迁入，2026-09-13 精简下沉）。
> 与 §5 的关系：§6 为**通用**冲突解决与豁免规则；§5 为其实例层的落地联动规则（身份判定/生命周期/继承与豁免），二者互补不重叠。

1. **层级冲突**：以高层级为准，登记至 `_temp/conflict-log.md`；`README.md` 与规约冲突时以 `AGENTS.md` 为权威修正
2. **同级冲突**：`docs/` 同级文档之间冲突，以 `AGENTS.md`（约束层）为准；`AGENTS.md` 无表述的双方标 `[存在差异]` 报用户裁定，不得擅删
3. **与实际状态冲突**：以实际为准；`README.md` 无约束力、`_temp/` 仅临时参考
4. **豁免**：高层级规则不适用时，须在 `AGENTS.md` 声明编号豁免条款，低层级以 `overrides` 引用

## 7. 源码 ↔ 规约同步规则

> 来源：G-4，承自 2026-09-02《规约体系结构性缺口》方案 §3.7（2026-09-13 落地；原拟定落点 AGENTS.md §7.7 为 09-06 精简前的旧章节号，已失效）。

本规则规定**源码变更时规约文档的同步义务**。**边界声明**：不将源码纳入规约管辖（`AGENTS.md` §5.1 条 6 不变），仅要求"改源码的同时评估并完成规约侧同步"。

**三类触发**

| # | 源码变更类型 | 必须评估/同步的规约载体 |
|---|--------------|--------------------------|
| ① | 新增或删除顶层模块/目录 | `AGENTS.md` §6 子目录职责边界表；视情新建实例文档并在 `knowledge/Instances-INDEX.md` 登记 |
| ② | 改公开接口或参数文件 Schema（`tables[]`+`steps[]`、`BUILTIN_OPS` 键与参数白名单） | `docs/architecture.md` 对应章节（Schema / 操作目录 / 数据传递规则） |
| ③ | 改 GUI 页面结构或阶段流程 | `docs/architecture.md` §8（生命周期与布局规格）+ `AGENTS.md` §5.3 |
| ④ | 改功能函数（用户操作）：`BUILTIN_OPS`／`STEP_CATALOG`（`_STEP_META_RAW`）／`_FORM_CLASSES`／`default_params()`／`STEP_KIND`／`OUTPUT_OPS`／`PRODUCE_LABEL` 任一 | `docs/function-spec-rules.md` §3.2 文档版记录表（增/改/删行）+ `docs/architecture.md` §6 清单；R7 新增，2026-09-24 |

**收尾检查清单**（编码类任务在任务记录中逐条确认）

1. 本次变更是否命中 ①②③④（逐类判定并写明结论）
2. 命中项对应文档是否已同步（未同步须写明原因与计划）
3. 变更后是否已执行 §4 全局更新校验机制
4. 未能同步的内容是否登记为 `[待补充]`（按 §4 的 `[待补充]` 机制处置）

**留痕要求**：任务记录「涉及文件汇总」表须含"规约同步"行，列明同步的文件与位置。

## 8. 验收与回归记录规范

> 来源：G-5，承自 2026-09-02 方案 §3.8（2026-09-13 落地，并作**事实校准**——见第 2 条）。

1. **验收节强制**：编码类任务的任务记录必须含 `## 验收` 节，逐条记录结果（通过 / 失败 / 阻塞）；与 `docs/task-records/TEMPLATE.md` 的"编码类任务须补验收节"提示对齐
2. **回归套件现状（2026-09-24 R6 事实校准，替代原"无现成回归套件"条款；2026-10-24 规模刷新）**：本仓库已有可复现自动化回归套件——`rpa_engine/tests/`（**263 用例，16 个测试文件**，2026-11-03 实测，`python -m unittest discover -s tests`）与门禁冒烟 `rpa_engine/tools/smoke/`（smoke_mb.py＝FF3 载体、smoke_m1m3.py＝FF4/FF5 载体；2026-09-24 经完善度修复轮 D8 裁定自 `_temp/DAG-rebuild/` 迁入正式工具目录并删除原件，恒真断言已修真）；`docs/architecture.md` §9 #4"端到端测试暂缓"仅指 `Test/` 端到端资源通道，不约束上述套件。`_temp/` 下一次性历史验证脚本（`bugfix*-verify-test.py`、`p1-acceptance-test.py`、`engine-smoke-test.py`、`dag-layout-test.py` 等，已于 2026-09-14 随清理删除，R4）**仍不得作为回归证据**，除非重新实际运行并留痕；`rpa_engine/tools/smoke/` 门禁脚本不在此限
3. **验收条目须经裁定**：验收条目以人工裁定的清单为准；计划文档中的回归清单（如 DAG 计划的真机回归单）在未经裁定前不得直接作为验收依据
4. **未通过不得关闭**：存在未通过项时任务**不得标「已完成」**，须改标「部分完成」并在要点摘要中列出遗留
5. **证据落点**：验收证据优先留 `_temp/verify-*.md`，任务记录内以路径引用，不复制全文
6. **禁用表述**：不得出现「回归套件」「58 项测试」「通过率」等暗示已有可复现套件的字样（历史"58 项"实为 8 个一次性脚本的 PASS 累加 19+7+6+7+3+4+4+4）
7. **降级验收**：确实无法执行运行期验证时，可采用"`py_compile` + 静态 grep 复核"的降级验收，并在验收节明确标注为降级（先例：2026-08-31 GUI 缺陷修复轮）

## 9. 标签体系落位规范

> 来源：W-14（2026-09-13 新增）。目的：消除"`AGENTS.md` §4.5/§4.7 定义了标签"与"文档实际用法不统一"之间的落差。

**两级落位**

| 层级 | 载体 | 适用 |
|------|------|------|
| 文档级 | YAML frontmatter 的 `binding` / `confidence` + 头部"约束力 / 可信度状态"声明行 | 表达整篇文档的约束力与可信度 |
| 段落 / 条目级 | 正文方括号标签 `[约束]` `[参考]` `[自包含指令]` `[待裁定]` | 仅在某段落或条目需就地提示时使用 |

**`binding` 四档 ↔ `AGENTS.md` §4.5 四标签映射**

| `binding` 取值 | 对应标签 | 适用文档 |
|-----------------|----------|----------|
| `constraint` | `[约束]` | `AGENTS.md` 及经 §2.5 背书的知识层文档 |

| `self_contained` | `[自包含指令]` | 实例层文档（正文自包含，不依赖跳转） |
| `pending_ruling` | `[待裁定]` | 含未裁定条目的方案态文档 |

**其它规则**

- `confidence` 取值 = `AGENTS.md` §4.7 六标签之一（含 `[方案态]`）
- 实例层文档必须同时含 `binding` 与 `confidence`
- **同一信息不得两种方式重复标注**；文档级优先，正文方括号标签仅在需要就地提示时使用

## 10. 约束层容量与下沉规则

> 来源：W-17（2026-09-13 新增），固化 2026-09-13 二轮精简的实测结论。

1. **计数口径**：`AGENTS.md` 长度一律按**含 CR 字符数**计（IDE 注入层的实测口径——CRLF 的 `\r` 也各计 1 字符）。统计方式：Python `len(open(p,'rb').read().decode('utf-8'))`。**不得使用 `wc -m`**（本机返回字节数，会得出相反结论）
2. **容量上限**：含 CR 字符数 **≤ 8,000**，建议余量 ≥ 200。**余量低于 200 时须先下沉等量细节到 `docs/` 再新增内容，禁止压缩保留块**（如 `AGENTS.md` §2.1/§2.2 红线本体）
3. **行尾约束**：`AGENTS.md` 必须保持 **CRLF**。仓库无 `.gitattributes` 且 `core.autocrlf=true`，改写为 LF 会在下次 `git checkout` 被展开回 CRLF，使字符数回升、注入截断复发——**不得以转换行尾的方式规避容量上限**
4. **下沉目标**：治理规则 → 本文件；构建与产物 → `docs/build-guide.md`；架构与 Schema → `docs/architecture.md`；实例细节 → 实例文档（经 `knowledge/` 索引登记）。`AGENTS.md` 只保留核心条款与指针
5. **变更后复测**：每次改动 `AGENTS.md` 后须复测三口径（含 CR / LF 归一化 / 行数）并记入任务记录（参照 2026-09-13 二轮精简：8,104 → 7,628）
